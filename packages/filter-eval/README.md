# @poe/filter-eval

Give it a `.filter` file and an item, get back the notes from every block that matched, in
order, following `Continue`.

It reads conditions and skips actions — colours, sounds, beams and icons never change what
matches. Each block carries a machine-readable `#@` note saying what it is for, and that
note is what comes back out. Nothing here knows what a bucket is.

This document is the contract a filter builder has to satisfy. Anything it does not
describe, the parser throws on.

## The one block shape

Every block looks like this, in this order:

```
Show
	Rarity Unique
	BaseType == "Heavy Belt"
	SetFontSize 45
	AreaLevel >= 68 # generated by bucket unique:Heavy Belt
	Continue
	#@ tier=T0 verb=check family=uniques-by-base bucket unique:Heavy Belt
```

| Part | Rule |
| --- | --- |
| Keyword | `Show`, `Hide` or `Minimal`, alone on the line. A trailing `#` comment is fine. |
| Conditions | One per line, any order. A trailing `#` comment is kept as provenance. |
| Actions | Optional, skipped, any order among the conditions. |
| `Continue` | Optional. Must come **before** the note. |
| `#@` note | Required, and must be the **last line of the block**. |

Four rules that reject a filter outright:

1. **Every block needs a `#@` note.** No exceptions, including a block the builder emits
   bare for spacing.
2. **The note is the last line.** A condition, action, `Continue` or a second `#@` after it
   throws.
3. **One note per block.** A second one cannot also be last.
4. **The note is the whole line.** `BaseType == "Gold" #@ tier=T0 verb=take` is a plain
   comment with no note in it, and the block then fails rule 1.

Blank lines and ordinary `#` comments may appear anywhere, including after the note.

## The note

```
#@ key=value key=value ... freehand text
```

The line, trimmed, starts with `#@` and a space. `#@tier=T0` without the space is an
ordinary comment and is ignored — there is no fuzzy prefix matching.

### Keys

| Key | Required | Values |
| --- | --- | --- |
| `tier` | yes | `T0` `T1` `T2` `T3` `T4` `T5` `varies` `hidden` |
| `verb` | yes | `take` `check` `gamble` |
| `family` | no | `bases` `corruptible-uniques` `div-cards` `foulborn` `fragments` `gems` `maps` `misc` `stackables` `unique-maps` `uniques-by-base` |

None of them repeat. An unknown key throws. A known key with an off-list value throws.

Keys are lowercase. **Values are case-sensitive** — `verb=Take` throws. This is the one
part of the format that cares, because a program writes it and a program has no excuse.

A value is `[^\s]+` — no spaces. There is no way to put a space in a `tier`, `verb` or
`family` value, and no need to.

## Extra conditions

A condition the generation phase adds is **an ordinary condition line**. There is no special
marker for it, on purpose: a marker would be a comment, the game would skip it, and the
filter being validated would not be the filter that runs.

Provenance goes in a trailing comment:

```
Show
	Rarity Unique
	BaseType == "Heavy Belt"
	AreaLevel >= 68 # generated by bucket unique:Heavy Belt
	Corrupted False # generated by bucket unique:Heavy Belt
	#@ tier=T0 verb=check family=uniques-by-base
```

Strip every comment from that file and what is left is a filter the game runs, condition for
condition. Nothing in the block means anything to the validator that does not also mean
something to the game.

The comment is kept on the condition as `condition.comment`, and the block header's comment
as `block.comment`, so a failing validation can say which bucket asked for the line. Nothing
reads them back apart from a person.

Because these are ordinary lines, they are validated like ordinary lines — a misspelled
condition or an off-list value throws at parse, naming the line.

A `#` inside a quoted value is part of the value, not the start of a comment, so
`BaseType == "Rune #3"` is safe.

### Freehand

Everything after the pairs is kept verbatim as debug text, on `block.freehand` and on each
entry of the result's `matched`. Put the bucket id here — an id like
`stack:currency/Mirror of Kalandra@1` has colons, slashes, spaces and an `@`, none of which
fit a note value.

**The freehand begins at the first token with no `=` in it.** A token that has an `=` but is
not a well-formed pair throws instead, so `Tier=T0` and `verb=Take` are caught rather than
swallowed as prose. Once the freehand has started the rest of the line is text, `=` and all:

```
#@ tier=T0 verb=take see stack>=3 here      freehand is "see stack>=3 here"
#@ tier=T0 verb=take stack>=3               throws: bad note pair "stack>=3"
```

So a freehand must not start with a word containing `=`. Lead with a plain word.

## Conditions

Condition names come from [docs/item-filter-syntax.md](../../docs/item-filter-syntax.md);
all 61 are supported. Each compares one of eight ways.

| Kind | Written | Item holds |
| --- | --- | --- |
| `boolean` | `Corrupted True` | `boolean` |
| `numeric` | `StackSize >= 5` | `number` |
| `ordered` | `Rarity > Magic`, `Rarity Normal Magic Rare` | `string` |
| `strings` | `BaseType "Chaos Orb" "Divine Orb"` | `string` |
| `enums` | `HasInfluence Shaper Elder` | `string[]` |
| `sockets` | `SocketGroup >= 5GGG` | `string`, e.g. `"RGB BB"` |
| `counted` | `HasExplicitMod >=2 "of Haast" "of Tzteosh"` | `string[]` |
| `gem` | `TransfiguredGem True`, `TransfiguredGem "Leap Slam"` | `string` |

Rules worth knowing before emitting:

- **`ordered` takes a list** on `=`/`==`/`!`/`!=` (`Rarity Normal Magic Rare` is any-of) but
  exactly one value when comparing with `<` `<=` `>` `>=`.
- **`strings` and `enums` match any of the listed values.** `!` and `!=` flip the whole
  condition, so none may match.
- **`sockets`**: the operator applies to the count, colours are always *at least*.
  `>= 5GGG` is five or more sockets with three or more green. Either half may be left out —
  `Sockets >= 3` and `Sockets >= AAAA` are both valid. Letters are `R G B A D W`.
- **`counted`**: the count may be glued (`>=2`) or spaced (`>= 2`). No count means one or
  more; a negated line with no count means none. `=0` means none of the listed names.
- **`gem`**: `True`/`False`, or a name.

### Operators

`=` `==` `!` `!=` `<` `<=` `>` `>=`, and the operator may be left out, defaulting to `=`.

**On text, `=` matches part of the name and `==` matches the whole name.** This matters
more than anything else here:

```
BaseType == "Gold"      matches Gold, not Gold Ring
BaseType "Gold"         matches Gold and Gold Ring
```

Emit `==` for anything identified by an exact base name, or buckets overlap.

Boolean, `strings`, `enums` and `gem` conditions take only the four equality operators.
Numeric and `ordered` take all eight.

### Case

Keywords, condition names, action names, `True`/`False`, enum and `ordered` values, and text
comparison are all **case-insensitive**. `show` and `SHOW` parse the same. Note values are
the exception, as above.

## Not supported

`Import` throws. Emit one file.

## Worked example

The bucket:

```json
{ "id": "unique:Heavy Belt", "family": "uniques-by-base", "verb": "check", "tier": "T0" }
```

The block:

```
Show
	Rarity Unique
	BaseType == "Heavy Belt"
	#@ tier=T0 verb=check family=uniques-by-base bucket unique:Heavy Belt
```

An item `{ Rarity: "Unique", BaseType: "Heavy Belt" }` comes back as verdict `Show` with
notes `{ tier: "T0", verb: "check", family: "uniques-by-base" }`.

## Using it

Write the note rather than building the string, so the writer and the reader cannot drift:

```ts
import { formatCondition, formatNote } from "@poe/filter-eval/format-note";

formatCondition("AreaLevel >= 68", "generated by bucket unique:Heavy Belt");
// AreaLevel >= 68 # generated by bucket unique:Heavy Belt

formatNote(
  { tier: "T0", verb: "check", family: "uniques-by-base" },
  "bucket unique:Heavy Belt",
);
// #@ tier=T0 verb=check family=uniques-by-base bucket unique:Heavy Belt
```

`formatNote` emits keys in a fixed order, so the same notes always produce the same line and
two generated filters compare as text. Both refuse anything the reader would reject.

Validate a generated filter by parsing it and asking it about an item:

```ts
import { parseFilter } from "@poe/filter-eval/parse-filter";
import { evaluateFilter } from "@poe/filter-eval/evaluate-filter";

const blocks = parseFilter(text);
const result = evaluateFilter(blocks, { Rarity: "Unique", BaseType: "Heavy Belt" });
```

`parseFilter` throwing is the first half of validation — every message names the line.
`result` is the second half:

| Field | Holds |
| --- | --- |
| `verdict` | `Show`, `Hide`, `Minimal`, or `none` if nothing stopped the walk |
| `notes` | the merged note, later blocks beating earlier ones |
| `contributions` | every note in the order given, each tagged with its block's line |
| `matched` | every block that matched, with its line, keyword and freehand |

`contributions` and `matched` are what a failing assertion should print: they name the block
that set a value, rather than only the value that came out wrong.

## Entry points

| Import | Gives |
| --- | --- |
| `@poe/filter-eval/parse-filter` | `parseFilter` |
| `@poe/filter-eval/evaluate-filter` | `evaluateFilter` |
| `@poe/filter-eval/format-note` | `formatNote`, `formatCondition` |
| `@poe/filter-eval/filter-ast` | `CONDITIONS`, `APPLY_KEYS`, `REQUIRED_KEYS`, `FilterItem` and the rest of the types |

`APPLY_KEYS` is the one place the note vocabulary lives. Adding a key is a line there.

## The item

`FilterItem` is a plain readonly object keyed by condition name, typed per condition kind,
so `{ Rarity: "Unique" }` compiles and `{ Rarity: 5 }` does not. It is everything a filter
can see — the grammar fixes its size, so it is not a model that gets outgrown.

**A missing key fails its condition, negation included.** `Corrupted ! True` on an item with
no `Corrupted` is `false`, not `true`. The item parser fills defaults in, so a gap here is a
real gap and the evaluator never guesses.
